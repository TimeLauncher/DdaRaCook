> 기준일: 2026-08-14  
> 기준 코드: `f572bac` (`dev/yohan`, `main`과 동일)  
> 목적: 지금까지 만든 것, 실제로 확인한 것, 앞으로 확인할 것을 누구나 빠르게 이해할 수 있게 정리한다.

## 1. 프로젝트를 한 문장으로 설명하면

**따라쿡은 스마트 안경으로 요리 상태를 짧게 촬영하고, AI가 실제 변화를 확인하면 음성으로 다음 단계를 안내하는 Android 요리 보조 앱이다.**

일반 레시피 앱처럼 정해진 시간이 지나면 무조건 다음 단계로 넘어가지 않는다. 예를 들어 “양파가 반투명해졌는가”를 시작 사진과 현재 사진으로 비교해 `DONE`, `NOT_DONE`, `CANNOT_TELL` 중 하나로 판정한다. AI가 확신하지 못하거나 시스템이 실패해도 사용자는 “다음”, “아직”, “이전”, “확인해줘” 같은 음성 명령과 화면 버튼으로 계속 요리할 수 있다.

## 3. 전체 동작 흐름

```text
사용자가 레시피 선택
        ↓
Meta 안경 연결 및 카메라 권한 확인
        ↓
현재 요리 단계 음성 안내
        ↓
필요한 시점에만 안경 카메라를 짧게 켜서 촬영
        ↓
사진 정규화
(회전 반영 → 위 40% 제거 → 긴 변 1024px → JPEG q80)
        ↓
폰 앱이 사진과 단계 조건을 판정 서버로 전송
        ↓
AI가 DONE / NOT_DONE / CANNOT_TELL 반환
        ↓
DONE 기준 횟수 충족 → 다음 단계
NOT_DONE → 현재 단계 유지 후 재검사
CANNOT_TELL 3회 → 자동 확인 중단, 수동 모드
        ↓
마지막 단계 후 소요 시간·판정·사진·수동 개입 요약
```

카메라는 조리 내내 켜 두지 않고 검사할 때만 사용한다. 이는 배터리, 발열, 개인정보 노출과 서버 비용을 줄이기 위한 핵심 설계다.

## 4. 지금까지 구현한 내용

### 4.1 Android 앱과 화면

- Jetpack Compose 기반 Android 앱을 만들었다.
- 홈, 레시피 상세, 레시피 편집, 안경 연결, 조리 진행, 단계 완료, 확인 필요, 수동 모드, 세션 요약 화면이 연결되어 있다.
- 대표 레시피와 여러 정적 예시 레시피를 제공한다.
- 사용자가 직접 레시피 단계, 완료 조건, 검사 시점과 재검사 간격을 편집할 수 있다.
- 앱을 종료했다 다시 열어도 진행 중이던 단계와 사용자가 만든 레시피를 복구한다.
- 단계별 소요 시간, 판정 결과, 수동 넘김, 이전 단계 복귀, 카메라 사용 시간과 캡처 사진을 요약 화면에서 볼 수 있다.
- 테스트용 정답을 입력해 정확도, 오탐과 미탐을 계산하는 흐름도 들어 있다.

현재 영속 저장은 명세에 적힌 Room이 아니라 **SharedPreferences JSON 방식**이다. 핵심 복구 기능은 동작하지만, Room 사용 자체가 인수 조건이면 별도 전환이 필요하다.

### 4.2 요리 상태 머신과 실패 대응

- 단계별 최초 검사 시점과 재검사 간격에 따라 자동 검사를 예약한다.
- A/B 등급 또는 단계 설정에 따라 연속 `DONE` 횟수를 채워야 자동 진행한다.
- `NOT_DONE`이면 현재 단계를 유지한다.
- `CANNOT_TELL`이 1~2회면 다시 볼 위치를 안내하고, 3회 연속이면 수동 모드로 전환한다.
- 네트워크 실패와 `CANNOT_TELL` 횟수를 분리한다. 따라서 인터넷이 잠시 끊겼다고 잘못 수동 모드로 전환되지 않는다.
- 촬영·판정 중 들어온 “다음” 명령도 버리지 않고 현재 작업을 정리한 뒤 처리한다.
- 중복 촬영, 오래된 서버 응답, 앱 재시작 중 남은 요청을 안전하게 무시하거나 정리한다.
- 안경이나 서버가 실패해도 레시피 안내와 수동 진행은 계속 사용할 수 있다.

### 4.3 음성 기능

- Android STT로 “다음”, “아직”, “다시”, “이전”, “확인해줘”를 처리한다.
- “재료 뭐야”, “이거 맞아?”, “몇 단계야”, “자동 확인 다시” 같은 보조 명령도 구현했다.
- Android TTS로 단계 시작, 검사 시작, 완료, 확인 불가와 오류 상황을 두 문장 이내로 안내한다.
- Vosk 기반 온디바이스 호출어 **“따라쿡”** 감지 코드를 추가했다.
- 호출어를 들으면 “네.”라고 응답하면서 바로 기존 명령 STT를 시작한다.
- 호출어용 한국어 모델은 최초 사용 때 무결성을 확인해 내려받고, 이후에는 오프라인으로 사용한다.

호출어 코드는 완성됐지만 실제 주방 소음, 후드 작동, 1~1.5m 거리에서의 성공률과 오인식률은 아직 측정하지 않았다.

### 4.4 Meta DAT 안경 카메라

- Meta Wearables DAT Android SDK 0.9.0을 프로젝트에 연결했다.
- 앱 등록, Bluetooth 권한, 안경 검색, 카메라 권한, 기기 세션과 준비 상태를 앱의 연결 화면에 연동했다.
- 실제 앱의 기본 경로는 `DatWearableCameraGateway`이며, 설정을 켠 디버그 빌드만 Fake 카메라를 사용한다.
- 검사 요청마다 짧은 스트림을 시작하고 첫 프레임 뒤 `capturePhoto()`를 호출한다.
- 촬영 사진을 앱 캐시에 저장해 `content://` URI로 상태 머신에 전달한다.
- 한 번에 하나의 촬영만 허용하고 시작·촬영·정리 각각에 타임아웃을 적용한다.
- 성공, 실패, 취소 모든 경우에 카메라와 foreground service를 정리한다.
- 단계 시작 기준 사진과 현재 검사 사진이 기존 요리 상태 머신으로 들어간다.
- 세션 종료나 이미지 삭제 시 앱이 소유한 캐시 사진도 정리한다.

다만 이 부분은 문서상 `CODE_COMPLETE_DEVICE_PENDING`이다. 즉, 코드는 있으나 **실제 안경으로 등록 → 촬영 → 서버 판정 → 음성 안내까지 이어지는 전체 성공을 아직 완료 처리하지 않았다.**

또한 현재 DAT 코드는 검증된 `MEDIUM · 24 FPS` 설정을 사용하지만 기능 명세는 `HIGH · 2 FPS`를 요구한다. 실제 기기 안정성과 화질을 측정한 뒤 하나로 합의해야 한다.

### 4.5 서버 전송 이미지 처리

서버에 보내는 사진에만 다음 처리를 한 번 적용한다.

1. PNG/JPEG를 디코딩한다.
2. EXIF 회전을 픽셀에 반영한다.
3. 화면 위쪽 40%를 잘라내고 조리 대상이 있는 아래쪽 60%를 남긴다.
4. 긴 변이 1024px보다 크면 비율을 유지해 축소한다. 작은 사진은 억지로 확대하지 않는다.
5. JPEG 품질 80으로 인코딩해 Base64로 전송한다.

파이프라인 버전은 `bottom60-long1024-jpeg80-exif-baked-v3`다. 3024×4032 테스트 입력이 크롭과 축소 후 1024×819 JPEG가 되는 것을 자동 테스트와 Android 계측 테스트로 확인했다. 원본 사진과 갤러리 사진은 변경하지 않는다.

남은 확인은 실제 DAT 사진이 같은 과정을 거쳐 서버에서 정상 JPEG와 예상 크기로 디코딩되는지 보는 것이다.

### 4.6 AI 판정 서버

- FastAPI 기반 `/judge-step`과 `/health` API를 구현했다.
- NVIDIA Nemotron 비전 모델을 실제 판정 백엔드로 연결했다.
- 시작 사진과 현재 사진을 함께 받는 다중 이미지 입력을 확인했다.
- 모델 응답이 조금 깨져도 안전하게 `DONE`, `NOT_DONE`, `CANNOT_TELL` 중 하나로 정리하는 파서를 만들었다.
- 대상이 안 보이거나 사진이 흐리면 확신해서 `DONE`이라고 하지 않도록 프롬프트를 설계했다.
- 요청 인증, JPEG 검사, 오류 코드, 429 백오프, 503·타임아웃 재시도와 응답 필드 검증을 구현했다.
- AI를 호출하지 않고 원하는 결과나 오류를 만드는 Mock 헤더가 있어 앱의 모든 분기를 요리 없이 시험할 수 있다.
- 문서상 Render의 `https://ddaracook-server.onrender.com`에 배포되어 있다.
- API 키와 팀 토큰은 소스가 아니라 환경변수와 추적되지 않는 로컬 설정에서 읽는다.
- push 전에 비밀값 유출을 검사하는 `server/check_secrets.sh`가 있다.

새 앱 설치 기준 실제 DAT 카메라와 실제 판정 서버가 기본값이고, Fake 카메라와 Fake 판정은 개발·오류 재현용으로 남겨 두었다.

- 원본을 보존하면서 평가용 이미지를 만드는 도구와 EXIF·ICC·크기를 점검하는 도구도 있다.

## 5. 대표 시연 레시피

현재 대표 레시피는 **소세지야채볶음(쏘야) 5단계**다.

| 단계 | 내용 | 자동 확인 방식 |
|---|---|---|
| 1 | 야채를 자르고 소세지에 칼집 내기 | 1분 뒤부터 손질 상태를 40초 간격으로 확인, `DONE` 2회 |
| 2 | 양념장 만들기 | 자동 판정 없이 “다음” 명령이나 버튼으로 진행 |
| 3 | 야채 볶기 | 2분 뒤부터 양파 색 변화를 20초 간격으로 비교, `DONE` 2회 |
| 4 | 소세지 볶기 | 2분 뒤부터 칼집이 처음보다 벌어졌는지 비교, `DONE` 2회 |
| 5 | 양념장 넣고 볶기 | 2분 50초 뒤 붉은 양념장 존재 확인, `DONE` 1회 |

1·3·4단계는 B등급이고 5단계만 A등급이다. 이는 “A등급 중심, B등급 1개”라는 원래 MVP 원칙과 다르므로 2회차 정확도 측정 결과에 따라 4단계를 더 쉬운 존재 판정으로 바꿀지 결정해야 한다.

## 7. 아직 해결하거나 합의해야 할 것

### 7.1 실제 안경 전체 흐름 검증

가장 먼저 아래 한 바퀴가 실제 기기에서 성공해야 한다.

```text
안경 등록·권한 → 스트림 시작 → 첫 프레임 → 사진 촬영
→ 이미지 정규화 → 실제 서버 판정 → 앱 상태 변경 → TTS → 카메라 종료
```

기능 명세의 기준은 `start → 3초 → capture → stop` 20회 중 19회 이상 성공이다. 성공·실패 후 카메라 표시등과 서비스가 항상 꺼지는지도 함께 확인해야 한다.

### 7.2 이미지와 판정 정확도 재평가

- 완료와 미완료가 균형 잡힌 실제 DAT 사진 20쌍 이상을 다시 촬영한다.
- 대표 레시피의 B등급 단계 정확도를 별도로 측정한다.
- 시작 사진 1장 추가가 정확도에 실제로 도움이 되는지 비교한다.
- 긴 변 1024px와 768px의 정확도·지연을 비교한다.
- 목표는 A등급 정확도 80% 이상이며, 가장 중요한 기준은 **잘못된 자동 진행 0회**다.

### 7.3 계약과 코드의 미합의 항목

- `CONTRACT.md` 머리말은 아직 버전 1.0·확정 대기라고 쓰여 있지만 변경 이력에는 1.2까지 있다. 세 사람의 합의 상태를 정리해야 한다.
- 계약은 `STATE_CHANGE`에 시작 사진을 보내지 않도록 정하지만, 대표 레시피 4단계는 “처음보다 칼집이 벌어졌는가”라서 시작 사진이 필요하다.
- 현재 앱도 계약에 맞춰 `COLOR_CHANGE`에만 시작 사진을 보내므로, 4단계는 필요한 비교 사진을 서버에 보내지 못한다.
- 이 문제는 계약을 먼저 합의해 개정한 뒤 앱 코드를 맞춰야 하며, 계약서를 한 사람이 임의로 수정하면 안 된다.
- 현재 카메라 설정 `MEDIUM · 24 FPS`와 명세의 `HIGH · 2 FPS`도 실측 후 통일해야 한다.

### 7.4 음성과 시연 환경

- 후드가 켜진 주방, 조리대에서 1.5m 거리로 명령 20회를 시험해 90% 이상 인식되는지 측정한다.
- 호출어 “따라쿡”의 오인식과 안내 TTS 도중 끼어들기가 실제 기기에서 동작하는지 확인한다.
- Render 무료 서비스는 잠들 수 있으므로 시연 전에 `/health`로 깨워야 한다.
- 시연용 서버에서 `DEBUG_MODE=false`인지 확인해 Mock 헤더로 결과를 조작할 수 없게 한다.
- 대표 레시피 전체 시연을 3회 연속 성공한 뒤 기능을 동결한다.

## 8. 권장 다음 순서

1. 실제 Meta 안경으로 S4 등록·권한·READY까지 확인한다.
2. 기준 사진 1회와 검사 사진 1회를 촬영해 캐시 저장과 정리를 확인한다.
3. 정규화된 실제 사진을 배포 서버로 보내 응답이 앱 상태와 음성에 반영되는지 확인한다.
4. 위 과정을 20회 반복해 카메라 안정성, 시작 지연, 왕복 지연과 사용률을 기록한다.
5. 실제 요리 완료·미완료 사진을 균형 있게 추가 촬영해 B등급과 1장/2장 비교를 끝낸다.
6. 결과를 바탕으로 `startImage`, 카메라 FPS·해상도, 대표 레시피 판정 유형을 세 명이 합의한다.
7. 주방 음성 시험과 전체 레시피 3회 리허설을 마친 뒤 최종 시연 버전을 고정한다.

## 9. 결론

따라쿡은 단순한 화면 시제품을 넘어 **레시피 앱, 상태 머신, 음성, 실제 DAT SDK 코드, 이미지 전처리, 배포된 AI 서버와 평가 도구까지 갖춘 통합 직전 단계**다. 지금 남은 핵심은 기능을 더 많이 만드는 일이 아니라, 실제 안경과 실제 요리 환경에서 전체 흐름이 안정적으로 반복되고 잘못된 자동 진행이 없는지 증명하는 일이다.
