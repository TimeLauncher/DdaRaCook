## 1. 전체 그림 — 요청 하나의 여행

판정 요청 **한 번**이 어떤 경로를 지나는지 따라가 봅시다.
"양파 볶기" 단계가 시작되고 2분이 지난 시점입니다.

```
┌─ 2번 (앱) ────────────────────────────────────────┐
│ ① 스케줄러: "단계 시작 후 120초 지났다. 검사할 때다" │
└───────────────────┬───────────────────────────────┘
                    │ camera.capture() 호출
┌─ 1번 (안경) ──────▼───────────────────────────────┐
│ ② 카메라 스트림 start → 2~3초 → 사진 촬영 → stop   │
│ ③ CaptureResult(imagePath, capturedAt, ...) 반환   │
└───────────────────┬───────────────────────────────┘
                    │ 사진을 base64로 인코딩
┌─ 2번 (앱) ────────▼───────────────────────────────┐
│ ④ JSON 조립 → POST /judge-step                    │
└───────────────────┬───────────────────────────────┘
                    │ 네트워크
┌─ 3번 (내 서버) ───▼───────────────────────────────┐
│ ⑤ 토큰 확인          → 틀리면 401/403              │
│ ⑥ Mock 헤더 있나?    → 있으면 즉시 반환 (개발용)    │
│ ⑦ 사진을 VLM 형식으로 포장 + 프롬프트 조립          │
│ ⑧ VLM API 호출 ─────────────────────┐             │
│                                     ▼             │
│                            [Nemotron / GPT]       │
│                                     │             │
│ ⑨ 응답 텍스트 수신 ◀────────────────┘             │
│ ⑩ JSON 파싱 → 실패해도 CANNOT_TELL로 안전 착지     │
│ ⑪ {verdict, reasonCode, latency, ...} 반환        │
└───────────────────┬───────────────────────────────┘
                    │ 네트워크
┌─ 2번 (앱) ────────▼───────────────────────────────┐
│ ⑫ verdict에 따라 결정:                            │
│    DONE 2회 연속 → 다음 단계                       │
│    NOT_DONE      → 20초 후 재검사                  │
│    CANNOT_TELL   → "잘 안 보여요" 안내             │
│ ⑬ TTS로 음성 출력 → 안경 스피커                    │
└───────────────────────────────────────────────────┘
```

### 이 그림에서 알아야 할 것

**내 담당은 ⑤~⑪뿐입니다.** 앞뒤는 1번·2번의 영역이에요.

그래서 내 서버는 **상태를 갖지 않습니다.** 지금이 몇 단계인지, 몇 번째 검사인지 전혀 모릅니다.
요청이 오면 사진을 보고 답하고 잊어버립니다. 이걸 **무상태(stateless)** 라고 합니다.

무상태라서 좋은 점:

- 데이터베이스가 필요 없음 (명세서 8.1: "서버 DB는 필요 없다")
- 서버가 재시작돼도 아무것도 잃지 않음
- 테스트가 쉬움 — 같은 입력이면 항상 같은 경로

## 2. 왜 이런 구조인가 — 설계 결정 3개

### 결정 1. 왜 서버를 따로 두는가

**API 키를 숨기기 위해서입니다. 그게 유일한 이유예요.**

| | 앱이 직접 AI 호출 | 서버를 거침 |
|---|---|---|
| 키 위치 | 앱 안 | 서버에만 |
| 앱을 뜯으면 | 키 유출 | 키 없음 |
| 결과 | 남의 돈으로 AI 사용 | 서버가 토큰으로 앱을 검증 |

그래서 서버가 **아주 얇아도 됩니다.** 로그인도, DB도, 관리자 페이지도 없습니다.
명세서 8.2절이 "단일 서버리스 함수 수준이면 충분하다"고 한 이유입니다.

### 결정 2. 왜 어댑터 구조인가

Nemotron으로 시작하지만 나중에 바꿀 수도 있습니다. 두 가지 방식이 있어요.

| | 서버 코드에 Nemotron 호출을 직접 작성 | `judge/` 폴더 안에만 벤더 코드를 가둠 |
|---|---|---|
| 교체 시 | 서버를 뜯어야 함 | 파일 하나 추가 + 환경변수 |

그런데 더 중요한 게 있습니다.

**어댑터 구조는 "교체 보험"이 아니라 그 자체가 산출물입니다.**

두 벤더를 동시에 꽂아두면 같은 테스트로 비교표를 뽑을 수 있습니다:

```
=== nemotron ===  정확도 58%  오탐 4건  지연 4200ms  비용 $0
=== openai   ===  정확도 84%  오탐 0건  지연 1800ms  비용 $0.31
```

이 표가 **"왜 이 모델을 선택했는가"에 대한 근거**이고, 발표 자료의 핵심입니다.
즉 어댑터는 나중을 위한 대비가 아니라, **지금 해야 할 일을 하기 위한 도구**예요.

### 결정 3. 왜 Mock을 먼저 만드는가

2번은 이런 코드를 짭니다:

```
CANNOT_TELL이 3번 연속 오면 → 수동 모드로 전환
```

이게 되는지 확인하려면 CANNOT_TELL을 정확히 3번 연속 받아야 합니다.
진짜 AI로는 이걸 만들 수가 없어요 — AI는 내 말을 안 듣습니다.
게다가 실제로 양파를 볶아야 하고요.

Mock 헤더가 있으면: **버튼 3번 클릭 → 10초 → 확인 끝.**

**2시간짜리 작업이 팀원의 일주일을 좌우합니다.** 그래서 T0-3이 첫날 최우선입니다.

### `.env` 와 `.env.example` 이 왜 둘 다 있나

| | `.env` | `.env.example` |
|---|---|---|
| 내용 | **진짜 키** | 빈 서식 |
| 커밋 | ❌ 절대 안 됨 | ✅ 함 |
| 목적 | 내 컴퓨터에서 실행 | 팀원이 "이런 값이 필요하구나" 알게 |

팀원이 저장소를 받으면 `.env.example`을 복사해 `.env`를 만들고 자기 키를 넣습니다.
**키는 절대 저장소에 들어가지 않습니다.**

## 4. 코드가 실제로 어떻게 동작하나

### 4.1 `server.py` 읽는 법

파일이 4덩어리로 되어 있습니다.

#### ① 계약 정의 — "이런 모양의 데이터만 받겠다"

```python
class JudgeRequest(BaseModel):
    requestId: str
    stepOrder: int
    checkType: CheckType          # 6개 값 중 하나만
    startImage: Optional[str]     # 없어도 됨
    currentImage: str             # 반드시 있어야 함
```

이게 단순한 "설명"이 아닙니다. **Pydantic이 자동으로 검사해줍니다.**

2번이 `stepOrder`를 빠뜨리고 보내면:

```
400 Bad Request
{"detail": [{"loc": ["body", "stepOrder"], "msg": "Field required"}]}
```

**내가 검증 코드를 한 줄도 안 썼는데** 어디가 틀렸는지까지 알려줍니다.
2번이 디버깅하기 쉬워지고, 나는 잘못된 데이터를 걱정할 필요가 없어집니다.

`CheckType`을 `Literal`로 선언한 것도 같은 이유예요.
`"COLORCHANGE"` (언더바 빠짐) 같은 오타가 서버 안까지 들어오지 못하고 입구에서 걸립니다.

#### ② 인증 — "우리 팀 앱이 맞나"

```python
def check_auth(authorization):
    if not authorization.startswith("Bearer "):  → 401
    if authorization[7:] != TEAM_TOKEN:          → 403
```

401과 403을 나눈 이유:

- **401** = 토큰을 아예 안 보냄 → "설정을 안 했구나"
- **403** = 토큰을 보냈는데 틀림 → "값이 잘못됐구나"

2번이 로그만 보고 원인을 알 수 있습니다.

#### ③ Mock 분기 — 개발용 지름길

```python
if DEBUG_MODE and x_mock_verdict:
    return 그 값 그대로
```

**AI를 호출하지 않고** 바로 반환합니다. 돈도 안 들고 즉시 응답합니다.

`X-Mock-Delay-Ms`도 있습니다. 지연을 흉내내서 2번이 **타임아웃 처리**를 테스트할 수 있게요.
`X-Mock-Delay-Ms: 9000`을 보내면 9초 걸리니, 2번의 8초 타임아웃이 제대로 발동하는지 확인됩니다.

> `DEBUG_MODE`가 붙어 있는 이유: 배포 후에는 `false`로 꺼야 합니다.
> 안 그러면 누구나 헤더 하나로 원하는 판정을 만들어낼 수 있습니다.

#### ④ 실제 판정 — 아직 비어 있음

```python
raise HTTPException(501, "실제 판정은 아직 연결되지 않았습니다 (T1-4 예정)")
```

**501을 고른 이유**가 있습니다.

| 코드 | 뜻 | 여기 쓰면 |
|---|---|---|
| 404 | 그런 주소 없음 | ❌ 주소는 있는데 오해 유발 |
| 500 | 서버가 터짐 | ❌ 버그로 착각함 |
| **501** | **아직 구현 안 됨** | ✅ 의도가 정확히 전달됨 |

2번이 로그에서 501을 보면 "아, 아직 안 만든 거구나"를 즉시 압니다.

### 4.2 `probe.py` 읽는 법

**이 스크립트의 목적은 딱 하나입니다: "이 모델이 이미지 2장을 동시에 받는가?"**

#### 왜 합성 이미지를 만드나

실제 요리 사진이 아직 없습니다(1번의 캡처 빌드를 받아야 촬영 가능).
그런데 T0-2는 지금 당장 해야 합니다. 그래서 스크립트가 **직접 그림을 그립니다.**

```
이미지 1                     이미지 2
┌─────────────┐            ┌─────────────┐
│ [파랑]       │            │ [빨강]       │  ← 판별용 표식
│             │            │             │
│      ⚪      │            │      🟠      │  ← 재료 (흰색 → 호박색)
│             │            │             │
│  (어두운 팬)  │            │  (어두운 팬)  │
└─────────────┘            └─────────────┘
```

두 가지를 동시에 노립니다:

| 요소 | 역할 |
|---|---|
| 가운데 원 (흰색→호박색) | **현실 흉내** — 양파가 투명해지는 상황 |
| 좌상단 사각형 (파랑→빨강) | **결정적 판별** — 두 장을 다 봤는지 확인 |

#### 왜 표식이 결정적인가

"두 사진의 차이를 말해줘"라고만 물으면 애매합니다.
모델이 한 장만 보고도 그럴듯하게 답할 수 있거든요.

그런데 이렇게 물으면:

> "각 이미지의 좌측 상단 사각형 색을 순서대로 말하세요"

**답에 파랑과 빨강이 둘 다 나와야만** 두 장을 받은 겁니다.
한 장만 받았으면 한 색밖에 말할 수 없어요. **빠져나갈 구멍이 없습니다.**

#### 4단계 검사와 그 순서

```
1. 텍스트 한 줄        → 인증이 되나?
2. 이미지 1장          → 이미지를 볼 수 있나?
3. 이미지 2장 ★        → 게이트. 둘 다 보나?
4. 실제 판정 프롬프트   → 우리 형식으로 답하나?
```

**순서가 중요합니다.** 3번이 실패했을 때 1·2번 결과가 있어야 원인을 압니다.

| 1 | 2 | 3 | 진단 |
|---|---|---|---|
| ❌ | – | – | 키나 주소가 틀림 |
| ✅ | ❌ | – | **텍스트 전용 모델을 골랐음** → 모델 다시 선택 |
| ✅ | ✅ | ❌ | 모델은 맞는데 다중 이미지 미지원 → 계획 분기 |
| ✅ | ✅ | ✅ | 통과 |

## 5. T0 단계별 상세 — 왜 이 순서인가

### 순서를 정한 원칙

```
1순위  남을 막고 있는 것       (내가 늦으면 팀원이 논다)
2순위  계획을 바꿀 수 있는 것   (일찍 알수록 손해가 적다)
3순위  리드타임이 긴 것         (남의 회신을 기다려야 한다)
4순위  나머지
```

**내 코드의 완성도보다 팀 전체의 처리량이 우선**이라는 뜻입니다.
3주짜리 프로젝트에서는 특히 중요합니다.

---

### T0-1 · NVIDIA 계정과 모델 조사

**하는 일**: 키 발급 + **이미지를 볼 수 있는 모델 ID 찾기**

**이 단계의 진짜 핵심은 두 번째입니다.**

Nemotron은 모델 **하나가 아니라 계열(family)** 입니다.
그 안에는 텍스트 전용도 있고 이미지도 보는 것도 있어요.
카탈로그에서 **vision / multimodal / VLM** 로 분류된 것만 후보입니다.

**여기서 텍스트 전용을 고르면** T0-2가 무조건 실패하고,
원인을 "다중 이미지 미지원"으로 오해하게 됩니다. 진단이 틀어져요.

**무료 한도를 확인하는 이유**:
W3에 대표 레시피를 10회 반복 테스트합니다. 세션당 20회 호출이면 200회,
개발 중 시행착오까지 더하면 500~1000회.
여기서 한도가 빠듯하면 **T2-5(유료 전환)를 앞당겨야** 합니다. 2주차에 알면 늦어요.

### T0-2 · 다중 이미지 확인 🚨 게이트

**하는 일**: `python probe.py` 실행

**왜 게이트인가**: 이 결과가 **프로젝트 계획을 바꿉니다.**

명세서 F4-7은 이렇게 주장합니다:

> 시작 시점과 현재를 함께 주고 "변화가 충분한가"를 묻는 편이 판정이 명확해진다.

이게 안 되면 색상 변화 판정을 포기해야 합니다.

**그런데 다행히 치명적이지는 않습니다.**

| 판정 유형 | 필요한 사진 | 이유 |
|---|---|---|
| 존재 여부 · 재료 식별 · 개수 · 상태 전환 | **1장** | 절대 판정 |
| 색상 변화 | **2장** | "반투명하다"는 상대적 개념 |

MVP 4~5단계 중 **2장이 필요한 건 1단계뿐**입니다.
실패해도 그 단계를 A등급으로 교체하면 프로젝트는 굴러갑니다.

**왜 1시간짜리를 이렇게 앞에 두나**: 실패했을 때 손해가 시간에 비례하기 때문입니다.
첫날 알면 계획만 고치면 되고, 2주차에 알면 코드를 버려야 합니다.

### T0-4 · API 계약서

**하는 일**: `CONTRACT.md` 작성 → 팀 합의

**왜 필요한가**: 2번이 **이 문서만 보고** 앱 코드를 짤 수 있어야 합니다.
문서가 없으면 2번이 계속 물어보거나, 추측해서 짜고 나중에 안 맞습니다.

**계약서에서 특히 중요한 3가지**

**① `startImage`는 null 가능**
비교가 필요 없는 유형에서 2장을 보내면 페이로드가 2배가 되어 3초 목표에 압박이 됩니다.

**② `vlmLatencyMs` ≠ `roundTripMs`**
서버가 잰 모델 시간과 앱이 잰 전체 왕복은 다른 값입니다.
이름을 안 나누면 평가할 때 **반드시 섞입니다.**
그리고 둘의 차이가 곧 네트워크 구간이라, 나눠두면 나중에
"느린 게 모델 탓인가 네트워크 탓인가"를 바로 알 수 있습니다.

**③ 네트워크 오류 ≠ CANNOT_TELL** ← 가장 많이 하는 실수

```
CANNOT_TELL   = AI가 사진을 봤는데 판단 못 함
네트워크 오류  = AI가 사진을 보지도 못함
```

이걸 섞으면 **와이파이가 잠깐 끊겼을 뿐인데** F4-5(3회 연속 → 수동 모드)에 걸립니다.
사용자 입장에선 "왜 갑자기 자동이 꺼졌지?"가 되고요.
2번이 카운터를 반드시 분리해야 합니다.

### T0-5 · 배포

**하는 일**: 어딘가에 올려서 URL 확보

**왜 첫날인가**: **"내 노트북에선 되는데" 문제를 첫날에 없애기 위해서**입니다.

로컬로만 개발하다 3주차에 배포하면 그때 처음 보는 문제가 쏟아집니다.
환경변수, 포트, 의존성, 방화벽… 시연 직전에 만날 문제가 아닙니다.

**무료 티어의 함정**: 15분 무응답이면 슬립에 들어가 첫 요청이 30초 이상 걸립니다.
그래서 T3-5에 "시연 전 워밍업"이 따로 있는 거예요.
`/health` 엔드포인트를 만든 이유이기도 합니다.

### T0-6 · 캡처 빌드 요청

**하는 일**: 1번에게 **"사진"이 아니라 "빌드"** 를 요청

3번도 안경이 있으니 촬영은 직접 합니다. 처음엔 "1번이 30쌍 찍어서 전달"로 잡았지만,
그러면 W2 전체(T2-1~T2-5)가 남의 일정에 묶입니다.

```
❌ 1번이 30쌍 전부 촬영       → 며칠 대기, W2 전체가 막힘
✅ 1번은 빌드 + 샘플 3~5쌍만  → 검증 후 나머지는 내가 촬영
```

**직접 찍는 게 왜 더 나은가**

라벨링을 하다 보면 **"이런 사진이 더 필요한데"를 반드시 발견합니다.**
손이 프레임을 가린 경우, 김이 서린 경우, 판정이 애매한 중간 상태 같은 것들이요.
카메라가 내 손에 있으면 20분이면 보충되고, 남의 일이면 또 한 바퀴 돕니다.

**그런데 하나는 바뀌면 안 됩니다**

> 사진이 **1번의 캡처·정규화 코드를 통과해서** 나와야 합니다.

명세서 12절의 "실제 DAT 결과를 쓰라"는 단순히 "안경으로 찍어라"가 아닙니다.
**평가 이미지와 실제 서비스 이미지가 같은 파이프라인을 통과해야** 한다는 뜻이에요.

제가 따로 파이썬 스크립트로 저장하면 JPEG 인코더·리샘플링·**EXIF 처리**가 달라집니다.
그러면 측정한 정확도 83%가 실제 서비스에서는 다른 숫자가 되고, **평가 리포트 전체가 무효**입니다.

그래서 1번에게 필요한 건 사진이 아니라 **캡처+정규화가 들어간 빌드**입니다.
명세서 10절 W0 실험 2(`start→3초→capture→stop` 20회) 코드를 그대로 주면 되니
1번 입장에서도 별도 작업이 거의 없습니다.

**검증 샘플 3~5쌍을 받는 이유**

1번 촬영본과 내 촬영본의 해상도·EXIF·포맷을 대조합니다.
이게 맞으면 나머지는 전부 내가 찍어도 안전해요.

**전체 의존을 소량 검증으로 바꾸는 것** — 실무에서 자주 쓰는 방법입니다.

**왜 실제 안경 사진이어야 하나**: 명세서 12절이 못박고 있습니다.

> 임의의 고화질 사진이 아니라 실제 DAT 스트림 또는 `capturePhoto()` 결과를 사용한다.

인터넷 사진으로 평가하면 정확도 95%가 나올 수 있습니다.
그런데 실제 안경 사진은 부엌 조명에 손이 가리고 김이 서리고 흔들립니다.
(해상도는 실측 결과 `capturePhoto()` 기준 2765×3687로 예상보다 높았습니다 —
720×1280은 *스트림* 해상도였습니다.)
**평가 조건이 실제와 다르면 그 숫자는 거짓말입니다.**

**EXIF 회전을 왜 그렇게 강조하나**

카메라는 종종 "사진은 그대로 두고, EXIF에 '90도 돌려서 봐라'라고 적어두는" 방식을 씁니다.

```
안드로이드 앱 → EXIF 읽음 → 똑바로 보임    ✅
내 서버 → AI  → EXIF 무시 → 누운 사진      ❌
결과: AI가 "팬이 안 보인다" → CANNOT_TELL 반복
```

**앱에서는 멀쩡한데 판정만 계속 실패하는** 형태로 나타납니다.
"내 프롬프트가 나쁜가?" 하고 프롬프트만 고치다 반나절을 날리는 대표적 함정이에요.

## 6. 앞으로 — W1 / W2 / W3의 의미

### W1 (T1-*) · 파이프라인 관통 — "일단 한 바퀴 돌린다"

**목표는 정확도가 아닙니다.** 명세서 10절이 명시적으로 말합니다.

> 목표는 정확도가 아니라 **한 바퀴가 도는 것**이다.

왜? **연결이 안 되는 문제가 정확도 문제보다 훨씬 무섭기 때문**입니다.
정확도는 프롬프트를 고치면 되지만, 세 사람 모듈이 안 붙으면 프로젝트가 없습니다.

| 태스크 | 의미 |
|---|---|
| T1-1 어댑터 규격 + JSON 파서 | 벤더 코드를 가둘 울타리를 먼저 침 |
| T1-2 Nemotron 어댑터 | 울타리 안에 첫 구현을 넣음 |
| T1-3 프롬프트 v1 | 좋을 필요 없음. **측정 기준점**을 만드는 것 |
| T1-4 실제 연결 | 501을 진짜 판정으로 교체 |
| T1-5 통합 테스트 | 폰 버튼 → 안경 → 서버 → 음성이 한 바퀴 |

**JSON 파서가 왜 T1-1에 있나**: 오픈 모델은 JSON 형식을 보장하지 않습니다.
코드블록으로 감싸거나 앞뒤에 설명을 붙일 수 있어요.

그래서 **관대한 파서**가 필요한데, 여기 안전 규칙이 하나 있습니다:

> **파싱 실패 시 절대 `DONE`으로 떨어지지 말 것. 무조건 `CANNOT_TELL`.**

명세서 목표가 "잘못된 자동 진행 0회"입니다.
못 읽었을 때 안전한 쪽으로 떨어지는 건 **설계 결정**이지 단순 예외 처리가 아닙니다.

### W2 (T2-*) · 정확도 — 여기가 3번 파트의 본체

| 태스크 | 의미 |
|---|---|
| T2-1 라벨링 | 사진에 정답을 답. **이게 있어야 채점이 가능** |
| T2-2 평가 스크립트 | 채점기. 한 줄 실행으로 지표가 나옴 |
| T2-3 프롬프트 개선 | v1→v2→v3. 실제로 정확도를 올리는 작업 |
| T2-4 1장 vs 2장 | **F4-7 가설 검증** |
| T2-5 벤더 비교 | 조건부. 모델 선정 근거 |
| T2-6 실패 대응 | 타임아웃·재시도 |
| T2-7 로그 포맷 | 2번의 로그를 내가 읽을 수 있게 |

**왜 T2-1(라벨링)이 먼저인가**: 정답이 없으면 채점을 못 합니다.
"AI가 DONE이라고 했다"만으로는 맞았는지 틀렸는지 알 수 없어요.

**T2-3에서 왜 같은 사진을 고집하나**

```
프롬프트 v1 → 밝은 낮에 찍은 사진으로 시험 → 61%
프롬프트 v2 → 어두운 밤에 찍은 사진으로 시험 → 74%
```

v2가 좋은 건가요, 사진이 쉬웠던 건가요? **알 수 없습니다.**
학생 실력을 비교하려면 같은 시험지를 줘야 하는 것과 같습니다.

**T2-4가 왜 중요한가**: 명세서 F4-7은 아직 **검증되지 않은 주장**입니다.
그걸 데이터로 확인하는 게 3번의 일이에요.

결과가 어느 쪽이든 성과입니다:

- 2장이 더 낫다 → 근거 확보, 발표 자료
- 차이가 없다 → **2장을 버림.** 페이로드 절반, 지연 감소. 이것도 훌륭한 발견

### W3 (T3-*) · 검증과 발표

| 태스크 | 의미 |
|---|---|
| T3-1 동결 | 더 이상 안 건드림. **시연 안정성 > 성능 개선** |
| T3-2 10회 반복 | 실기기 실측 |
| T3-3 리포트 | 숫자로 증명 |
| T3-4 발표 자료 | |
| T3-5 시연 안정화 | 워밍업, 폴백 |

**왜 동결하나**: 3주차에 "조금만 더 좋게"는 시연을 망치는 가장 흔한 원인입니다.
명세서 10절도 "실제 시연 3회 연속 성공 후 기능 동결"이라고 못박고 있어요.

## 7. 계속 나오는 핵심 개념 6개

### ① 계약 (Contract)

세 사람이 각자 개발하다 마지막에 붙이려면,
**"너는 나한테 이런 모양을 준다"** 를 미리 못박아야 합니다.
콘센트 규격 같은 거예요. 규격만 맞으면 뭐가 꽂히든 상관없습니다.

`CONTRACT.md`가 그 규격이고, **첫날 정하고 이후 안 바꾸는 것**이 핵심입니다.

### ② Mock

**하드웨어가 없어서 쓰는 대용품이 아닙니다.** 원하는 상황을 마음대로 만드는 도구입니다.

안경이 3대 있어도 CANNOT_TELL을 3번 연속 나오게 할 수는 없고,
양파를 볶는 데는 30분이 걸립니다. Mock은 그걸 10초로 줄입니다.

### ③ 게이트 태스크

**결과에 따라 계획이 바뀌는 실험**입니다. 무조건 먼저 합니다.
손해가 시간에 비례해서 커지기 때문이에요.

### ④ 오탐 vs 미탐

```
오탐 = 아닌데 맞다고 함  → 안 익었는데 DONE   → 다음 단계 → 요리 망함  ☠️
미탐 = 맞는데 아니라고 함 → 다 익었는데 NOT_DONE → 좀 기다림          😐
```

**"정확도 80%"로는 부족합니다.** 어느 방향으로 틀리는지가 훨씬 중요해요.
명세서 12절 목표가 두 개인 이유입니다:
"A등급 80% 이상" **그리고** "잘못된 자동 진행 0회".

### ⑤ CANNOT_TELL vs 네트워크 오류

```
CANNOT_TELL   = AI가 봤는데 판단 못 함 → 3회면 수동 모드 (F4-5)
네트워크 오류  = AI가 보지도 못함       → 재시도, 카운터 건드리지 않음
```

섞으면 와이파이 끊김이 수동 모드 전환을 유발합니다. 카운터를 분리하세요.

### ⑥ 고정 테스트 세트

같은 시험지로 시험을 봐야 실력 비교가 됩니다.
프롬프트를 바꿀 때마다 새 사진을 쓰면 **개선했는지 알 수 없습니다.**

## 8. 자주 헷갈리는 것들

**Q. 서버가 "얇다"는 게 무슨 뜻인가요?**
DB도 로그인도 관리자 페이지도 없이 엔드포인트 하나만 있다는 뜻입니다.
`/judge-step` 하나 + 확인용 `/health` 하나. 그게 전부예요.

**Q. `promptVersion`과 `backend`를 응답에 왜 넣나요?**
나중에 로그를 볼 때 "이 판정은 어떤 프롬프트, 어떤 모델이 한 거지?"를 알기 위해서입니다.
넣는 데 1초, 없으면 나중에 데이터가 쓸모없어집니다.

**Q. `requestId`는 왜 필요한가요?**
