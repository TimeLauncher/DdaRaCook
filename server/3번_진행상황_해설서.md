## 1. 이 서버가 하는 일은 딱 한 가지

### 1.1 경계선 긋기

3명이 만드는 시스템에서 **3번(나)의 담당은 아주 좁습니다.**

```
1번: 안경 카메라로 사진을 찍어 파일로 남긴다
2번: 그 사진을 base64로 만들어 서버에 보내고, 답을 받아 앱 상태를 바꾼다
3번: ★ 사진을 받아 "이 단계 끝났어?"에 한 단어로 답한다  ← 여기만
```

내 서버는 **무상태(stateless)** 입니다. 지금이 몇 단계인지, 아까 뭐라고 답했는지 전혀 기억하지 않습니다.
요청이 오면 사진을 보고 답하고 잊어버립니다.

- 데이터베이스가 필요 없습니다 (명세서 8.1)
- 서버가 재시작돼도 잃을 게 없습니다
- "연속 DONE 2회면 다음 단계로" 같은 **판단은 전부 2번(앱)의 몫**입니다

### 1.2 요청 하나의 여행 — 코드 위치와 함께

```
[2번 앱]  POST /judge-step  { requestId, checkType, checkCondition,
                              elapsedSeconds, startImage?, currentImage }
                │
                ▼
 server.py:192  judge_step()  ── 요청 함수 진입
                │
                ├─ ① check_auth()            Bearer 토큰 확인 → 401 / 403
                │
                ├─ ② X-Mock-Status 헤더?     있으면 그 오류를 즉시 반환 (AI 호출 X)
                ├─ ③ X-Mock-Verdict 헤더?    있으면 그 판정을 즉시 반환 (AI 호출 X)
                │                            └ 여기까지가 T0-3 "Mock 서버"
                │
                ├─ ④ checkType == TIME_ONLY? → 400 (앱이 로컬 타이머로 처리할 유형)
                │
                ├─ ⑤ _validate_image()       base64 디코드 + JPEG 매직바이트 검사 → 400
                │
                ├─ ⑥ get_judge()             환경변수에 맞는 어댑터 1개 가져오기 (캐시)
                │
                ├─ ⑦ prompts.build_user_text()  단계 내용·완료 조건·경과시간을 한 덩어리로
                │
                ├─ ⑧ judge.judge(...)        ── judge/nemotron.py:126
                │      │                        이미지를 API 형식으로 포장 → NVIDIA 호출
                │      │                        7.5초 예산 안에서 재시도 관리
                │      └─ 실패 시 JudgeError 를 raise (Verdict 로 바꾸지 않음! ★)
                │
                ├─ ⑨ coerce_verdict()        ── judge/base.py:224
                │                               모델이 뱉은 텍스트 → {verdict, reasonCode}
                │                               못 읽으면 CANNOT_TELL 로 안전 착지
                │
                ├─ ⑩ _log()                  한 줄 로그 (이미지는 절대 안 찍음)
                │
                ▼
[2번 앱]  200 { verdict, reasonCode, vlmLatencyMs, promptVersion, backend }
          또는 400 / 401 / 403 / 429 / 500 / 503 + { detail: "설명" }
```

이 흐름에서 **초보자가 가장 놓치기 쉬운 갈림길**이 ⑧과 ⑨ 사이에 있습니다.

- ⑨ 로 갔다 = **모델이 사진을 봤다.** 답이 이상해도 그건 "판정 결과"다 → 200 응답
- ⑧ 에서 예외 = **모델이 사진을 보지도 못했다.** 이건 판정이 아니다 → 503 응답

이 둘을 섞으면 안 되는 이유는 §4.2 에서 자세히 다룹니다. 이 프로젝트에서 **가장 중요한 설계 규칙**입니다.

### 초보자용 감각 잡기: "왜 파일이 이렇게 많은가"

파일을 나누는 기준은 **"바뀌는 이유"** 입니다. 같이 바뀌는 것끼리 묶고, 따로 바뀌는 것은 떼어놓습니다.

| 이 파일은 언제 바뀌나 | 파일 |
|---|---|
| API 계약이 바뀔 때 | `server.py` |
| 프롬프트를 개선할 때 (T2-3에서 3~4번 예정) | `prompts.py` 만 |
| 모델 벤더를 갈아탈 때 (T2-5 조건부) | `judge/` 안에 파일 1개 추가 |
| 평가 지표를 추가할 때 | `eval.py` 만 |

프롬프트를 고치려고 `server.py` 를 열어야 한다면 그건 잘못 나뉜 것입니다.
T2-3 은 프롬프트를 여러 번 바꿔 성능을 비교하는 작업인데, 그때마다 서버 코드를 건드리면
"프롬프트가 좋아진 건지 서버 코드가 바뀐 건지" 구분할 수 없게 됩니다.

## 3. Phase 0 — 생존 실험 (D1~D2)

> **원칙: 내 코드 완성도보다 팀을 막고 있는 것을 먼저 푼다.**

### 3.1 T0-1 · 모델 조사 → `notes/nemotron.md`

확인한 것:

| 항목 | 결과 |
|---|---|
| Base URL | `https://integrate.api.nvidia.com/v1` |
| **OpenAI 호환 여부** | ✅ **예** — 파이썬 `openai` 패키지를 그대로 사용 가능 |
| 전체 모델 수 | 102개 (이름 기준 비전 모델 12개) |

**"OpenAI 호환"이 왜 중요한가** — API 규격이 회사마다 다르면 벤더를 바꿀 때 코드를 새로 짜야 합니다.
NVIDIA 가 OpenAI 와 같은 요청/응답 모양을 쓰기 때문에, 나중에 진짜 OpenAI 로 갈아탈 때
`base_url` 과 `model` 문자열만 바꾸면 됩니다. 이 사실 하나가 T2-5(백업 계획)의 비용을 4시간에서 30분으로 줄입니다.

### 3.2 T0-2 · 🚨 게이트 태스크 — 다중 이미지 지원 확인 (`probe.py`)

**게이트 태스크**란 "결과에 따라 이후 계획 자체가 바뀌는 실험"입니다. 다른 코드보다 먼저 합니다.

명세서 F4-7 은 *"시작 사진과 현재 사진을 함께 주고 변화를 묻는 게 낫다"* 고 주장합니다.
그런데 **모델이 한 요청에 이미지 2장을 못 받으면 이 기능은 아예 불가능**합니다.
2주 뒤에 발견하면 계획을 통째로 갈아엎어야 하므로 첫날에 확인했습니다.

**실험 설계가 이 태스크의 핵심입니다.**

```
❌ 나쁜 설계: 사진 2장 넣고 "차이를 말해줘"
   → 모델이 한 장만 보고도 그럴듯한 답을 지어낼 수 있다. 통과인지 아닌지 알 수 없다.

✅ 좋은 설계: 파란 사각형 이미지 + 빨간 사각형 이미지를 넣고
   "각 이미지 좌상단 사각형 색을 순서대로 말해줘"
   → 두 색을 다 맞혀야만 두 장을 받은 것이다. 빠져나갈 구멍이 없다.
```

이것이 **판별 가능한(falsifiable) 실험**입니다. 결과:

| 모델 | 결과 |
|---|---|
| `nvidia/nemotron-nano-12b-v2-vl` | ✅ 통과 — "파란색, 빨간색" 정확 |
| `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` | ✅ 통과 (그러나 지연 41초 → 실격) |
| `nvidia/llama-3.1-nemotron-nano-vl-8b-v1` | ⚠️ 2장은 받으나 색 판별 부정확 ("파랑"→"보라") |
| `meta/llama-3.2-11b / 90b-vision-instruct` | ❌ **다중 이미지 미지원** (API 가 거부) |

> 📌 배운 것: **이름에 "vision" 이 있다고 이미지 2장을 받는 게 아닙니다.**
> Llama 3.2 Vision 계열은 아키텍처상 한 요청에 1장만 받습니다. 문서만 읽고 넘어갔으면 몰랐을 사실입니다.

**게이트 통과** → F4-7 검증을 포기하지 않아도 되고, COLOR_CHANGE 단계를 A등급으로 교체하는 우회안이 불필요해졌습니다.

### 3.3 T0-3 · Mock 서버 — 팀 블로커 해제

2번(앱 담당)은 서버가 없으면 상태 머신을 테스트할 수 없습니다.
그런데 진짜 AI 판정을 붙이려면 며칠이 걸립니다. 그래서 **껍데기부터 먼저** 만들었습니다.

```python
# server.py:219
if DEBUG_MODE and x_mock_verdict:
    v = x_mock_verdict.strip().upper()
    ...
    return JudgeResponse(verdict=v, reasonCode=reason,
                         vlmLatencyMs=delay, promptVersion="mock", backend="mock")
```

헤더 한 줄이면 원하는 답이 즉시 옵니다.

```bash
curl -X POST .../judge-step -H "X-Mock-Verdict: CANNOT_TELL" ...
```

이게 있으면 2번은 **실기기도, 실제 요리도, AI 도 없이** 다음을 테스트할 수 있습니다.

| 명세서 기능 | 테스트 방법 |
|---|---|
| F4-3 연속 DONE 2회 → 자동 진행 | `X-Mock-Verdict: DONE` 2회 |
| F4-5 CANNOT_TELL 3회 → 수동 모드 | `X-Mock-Verdict: CANNOT_TELL` 3회 |
| 타임아웃 fallback | `X-Mock-Delay-Ms: 9000` |
| 모델 타임아웃(503) 분기 | `X-Mock-Status: 503` ← T1 에서 추가 |

**초보자용: FastAPI + Pydantic 이 여기서 뭘 해주나**

```python
class JudgeRequest(BaseModel):
    requestId: str
    stepOrder: int
    checkType: CheckType        # Literal["PRESENCE","COUNT",...]
    currentImage: str
```

이렇게 클래스 하나만 선언하면 FastAPI 가 자동으로:

1. JSON 을 파싱하고
2. `stepOrder` 에 문자열이 오면 **422 오류를 자동으로** 돌려주고
3. `checkType` 에 오타가 있으면 "가능한 값은 이것들"이라고 알려주고
4. `/docs` 에 브라우저로 열어볼 수 있는 API 문서를 만들어 줍니다

**검증 코드를 한 줄도 안 써도 됩니다.** 엔드포인트 1개짜리 서버에 FastAPI 를 고른 이유입니다.

### 3.4 T0-4 · API 계약서 `CONTRACT.md`

**계약(Contract)** 은 "이 모양의 데이터를 주고받자"는 팀 간 약속 문서입니다.
계약서가 없으면 2번은 서버가 완성될 때까지 아무것도 못 만듭니다.
계약서가 있으면 **양쪽이 동시에** 만들 수 있습니다. 이게 계약서의 존재 이유 전부입니다.

계약서에 못 박은 것 중 초보자가 놓치기 쉬운 두 가지:

**① `vlmLatencyMs` 와 `roundTripMs` 는 다른 값이다 — 이름부터 분리**

```
앱이 잰 왕복 시간 (roundTripMs)  = 업로드 + [서버 시간] + 다운로드
서버가 잰 모델 시간 (vlmLatencyMs) =               ↑ 이 구간만
                                     둘의 차이 = 네트워크 구간
```

이름을 하나로 통일하면 나중에 "3초를 못 맞추는데 원인이 모델인지 업로드인지"를 영영 알 수 없습니다.

**② 앱은 모르는 `reasonCode` 가 와도 크래시하면 안 된다**

나중에 reasonCode 를 하나 추가했을 때 구버전 앱이 죽지 않게 하는 장치입니다.

### 3.5 T0-5 · 배포

## 4. Phase 1 — 진짜 판정 연결 (코드의 핵심)

여기가 실제 코드 분량의 대부분입니다. 천천히 봅시다.

### 4.1 어댑터 패턴 — "벤더를 한 폴더에 가두기"

**문제 상황**: Nemotron 이 정확도 미달이면 OpenAI 로 갈아타야 합니다.
그때 서버·평가 스크립트·프롬프트를 전부 고쳐야 한다면, 갈아타는 데만 며칠이 걸립니다.

**해결**: 벤더 종속 코드를 `judge/` 안에만 두고, 바깥은 **규격(Protocol)** 만 알게 합니다.

```python
# judge/base.py:89
@runtime_checkable
class VlmJudge(Protocol):
    name: str    # "nemotron" / "openai"
    model: str

    def judge(self, system: str, user_text: str,
              start_b64: Optional[str], current_b64: str) -> Verdict: ...
```

`Protocol` 은 파이썬의 **"이 모양만 갖추면 뭐든 받아준다"** 는 선언입니다.
자바의 인터페이스와 비슷하지만, 상속을 강제하지 않습니다.
`name`, `model`, `judge()` 세 개만 있으면 어떤 클래스든 어댑터가 될 수 있습니다.

실제로 그 덕분에 `judge/mock.py`(가짜 어댑터)가 `NemotronJudge` 를 상속하지 않고도
`eval.py` 에서 똑같이 동작합니다.

**팩토리와 캐시**:

```python
# judge/__init__.py:76
_BACKENDS = {"nemotron": _make_nemotron, "openai": _make_openai, "mock": _make_mock}
_cache: dict[str, VlmJudge] = {}

def get_judge(backend=None):
    name = (backend or os.getenv("VLM_BACKEND") or DEFAULT_BACKEND).strip().lower()
    if name not in _cache:
        _cache[name] = _BACKENDS[name]()
    return _cache[name]
```

- 새 벤더 추가 = `_BACKENDS` 에 한 줄 + 파일 1개. 서버와 `eval.py` 는 한 글자도 안 바뀜
- **캐시하는 이유**: 어댑터 1개 생성 = HTTP 클라이언트 1개 생성입니다.
  요청마다 만들면 커넥션 풀이 매번 새로 떠서 느려집니다
- **앱 시작 시점이 아니라 첫 요청 때 만드는 이유**: 키가 없어도 서버는 떠야 합니다.
  Mock 경로는 키 없이 동작해야 2번이 테스트할 수 있으니까요

### 4.2 ★ 가장 중요한 설계 규칙 — `CANNOT_TELL` 과 오류를 절대 섞지 않는다

이 프로젝트 전체에서 **딱 하나만 기억해야 한다면 이것**입니다.

```
CANNOT_TELL  = AI 가 사진을 봤는데 판단을 못 함     ← 정상적인 판정 결과
JudgeError   = AI 가 사진을 보지도 못함             ← 판정이 아님 (네트워크·타임아웃·키 오류)
```

**왜 섞으면 안 되나**: 명세서 F4-5 는 "CANNOT_TELL 이 3회 연속이면 수동 모드로 전환"입니다.
와이파이가 잠깐 끊긴 걸 CANNOT_TELL 로 바꿔 세면, **네트워크가 불안정할 뿐인데
사용자가 수동 모드로 쫓겨납니다.** 그리고 실측상 타임아웃은 드물지 않게 발생합니다(§4.7).

그래서 예외 계층을 이렇게 만들었습니다.

```python
# judge/base.py:60
class JudgeError(RuntimeError):        http_status = 503   # 모델 호출 자체가 실패
class JudgeConfigError(JudgeError):    http_status = 500   # 키 누락·모델 ID 오타 (재시도 무의미)
class JudgeTimeout(JudgeError):        http_status = 503   # 시간 내 응답 없음
class JudgeRateLimit(JudgeError):      http_status = 429   # 무료 한도
class JudgeUpstreamError(JudgeError):  http_status = 503   # 벤더 5xx·연결 실패
```

**예외 클래스에 HTTP 상태 코드를 붙여둔 게 요령**입니다. 서버는 분기 없이 한 줄로 처리합니다.

```python
# server.py:270
except JudgeError as e:
    # 🚨 여기서 절대 CANNOT_TELL 을 반환하지 않는다
    raise HTTPException(getattr(e, "http_status", 503), str(e))
```

같은 규칙이 `eval.py` 에도 있습니다. 호출 실패는 **정확도 분모에서 제외**합니다.
안 그러면 네트워크 사고가 "모델 성능 저하"로 둔갑합니다.

```python
# eval.py:295
graded = [o for o in outcomes if not o.error]   # 호출 실패는 분모에서 뺀다
```

그리고 2번이 이 규칙을 실제로 지켰는지 확인할 수단까지 만들었습니다(`X-Mock-Status`).

```
X-Mock-Verdict: CANNOT_TELL  ×3  → 수동 모드로 전환되어야 함  (정상)
X-Mock-Status:  503          ×3  → 수동 모드로 가면 안 됨      (가면 카운터가 합쳐진 것)
```

### 4.3 관대한 JSON 파서 (`coerce_verdict`)

**문제**: 오픈 모델은 JSON 형식을 보장하지 않습니다. 실측에서 12b 모델은 3회 중 1회
JSON 앞에 설명 문장을 붙였습니다. 이런 응답들이 실제로 옵니다.

```
① {"verdict": "DONE", "reasonCode": "VISIBLE_CHANGE"}          ← 이상적
② ```json\n{"verdict": "NOT_DONE"}\n```                        ← 코드블록으로 감쌈
③ 사진을 확인한 결과... {"verdict": "NOT_DONE"} 조금 더 볶으세요  ← 설명이 붙음
④ {"verdict": "DONE", "reasonCode":                            ← 토큰 한도로 잘림
⑤ {"verdict": "DONE | NOT_DONE | CANNOT_TELL"}                 ← 템플릿을 그대로 따라 씀
```

`json.loads()` 하나로는 ①만 처리됩니다. 그래서 4단계로 시도합니다.

```
① ```json ... ``` 코드블록이 있으면 그 안쪽을 우선 후보로
② 괄호 균형 스캐너로 {...} 후보를 바깥쪽부터 추출
③ 홑따옴표·후행 쉼표 정도는 고쳐서 재시도
④ 전부 실패 → CANNOT_TELL (parsed=False)
```

**②의 괄호 균형 스캐너를 직접 만든 이유** — 정규식 `\{.*\}` 로 하면 이런 응답에서 깨집니다.

```json
{"reason": "팬 {안} 재료가 보입니다"}
```

문자열 리터럴 안의 중괄호까지 세어 버리기 때문입니다. 그래서 문자열 안인지 아닌지를
추적하며 한 글자씩 스캔합니다.

```python
# judge/base.py:140
for i, ch in enumerate(text):
    if in_str:                       # 문자열 안이면 괄호를 세지 않는다
        if escape: escape = False
        elif ch == "\\": escape = True
        elif ch == '"': in_str = False
        continue
    if ch == '"': in_str = True
    elif ch == "{":
        if depth == 0: start = i
        depth += 1
    ...
```

또 모델이 키 이름을 조금씩 바꿔 부르는 것까지 받아줍니다.

```python
_VERDICT_KEYS = ("verdict", "result", "judgment", "judgement", "decision")
_REASON_KEYS  = ("reasoncode", "reason", "reasoncodes", "why")
```

`reason_code`, `Reason-Code`, `REASONCODE` 모두 정규화해서 같은 키로 봅니다.
그리고 `{"result": {"verdict": ...}}` 처럼 한 겹 감싸는 경우를 대비해 **깊이 3까지** 파고듭니다.

#### ★ 파서의 진짜 목적은 "잘 읽는 것"이 아니다

```python
SAFE_FALLBACK = "CANNOT_TELL"
```

명세서 12절의 목표는 **두 개**입니다. "정확도 80%" 그리고 **"잘못된 자동 진행 0회"**.
파싱 실패를 DONE 으로 처리하면 후자가 즉시 무너집니다.

그래서 `test_parser.py` 의 진짜 테스트는 케이스 16개가 아니라 **마지막의 불변식**입니다.

```
── 불변식: 쓰레기 입력에서 DONE 금지 ──
✅ 통과 (16종 쓰레기 입력)
```

케이스 4번을 보면 의도가 분명합니다.

```python
("4. 깨진 JSON",
 '{"verdict": "DONE", "reasonCode":',
 "CANNOT_TELL", "OTHER"),          # ★ DONE 이 보여도 절대 DONE 이면 안 된다
```

문자열 안에 `DONE` 이 뻔히 보이지만, **읽어내지 못한 응답은 DONE 이 될 수 없습니다.**

### 4.4 Nemotron 어댑터 — 시간 예산이라는 개념

이 파일이 아는 것: 이미지 포장, 타임아웃, 재시도, 예외 분류.
이 파일이 모르는 것: 프롬프트 내용, 판정 규칙.

**① 이미지 포장**

OpenAI 호환 API 는 이미지를 `data:` URL 형태로 받습니다.

```python
# judge/nemotron.py:97
{"type": "image_url",
 "image_url": {"url": f"data:image/jpeg;base64,{normalize_b64_image(b64)}"}}
```

**② 라벨을 끼워 넣는 이유**

```python
blocks = [
    {"type": "text", "text": "이미지 1 — 단계를 시작한 시점:"},
    이미지1,
    {"type": "text", "text": "이미지 2 — 현재:"},
    이미지2,
    {"type": "text", "text": user_text},     # 질문은 맨 뒤
]
```

라벨이 없으면 모델은 **어느 쪽이 '이전'인지 모릅니다.** 순서만으로는 전달되지 않습니다.
그리고 **질문을 이미지 뒤에 두는 것**도 의도적입니다. 앞에 두면 모델이 이미지를 보기 전에
답을 정해버리는 경향이 있습니다.

**③ 시간 예산 (초보자가 가장 헷갈리는 부분)**

앱 타임아웃은 계약서상 8초입니다. 서버가 "8초짜리 시도"를 2번 하면 16초가 되어,
앱은 이미 포기한 뒤입니다. 그래서 **총 예산 7.5초를 여러 시도가 나눠 씁니다.**

```python
DEFAULT_TIMEOUT_S = 7.5   # 앱(8초)보다 짧게
MIN_ATTEMPT_S     = 1.5   # 이보다 적게 남았으면 재시도해봐야 헛수고
RETRY_SLEEP_S     = 0.3

t0 = time.monotonic()
deadline = t0 + self.timeout_s
while True:
    remaining = deadline - time.monotonic()
    if remaining < MIN_ATTEMPT_S:
        raise JudgeTimeout(...)
    resp = self._client.chat.completions.create(..., timeout=remaining)  # 남은 만큼만
```

- 연결 실패·5xx 처럼 **빨리 실패하는** 오류 → 예산이 남으므로 1회 재시도
- 진짜 타임아웃 → 예산 소진, 재시도 없이 503

**왜 앱보다 0.5초 짧게 잡나** — 같게 두면 앱은 서버의 503 메시지 대신 자기 쪽 소켓 타임아웃을
보게 됩니다. 그러면 앱 로그만으로는 "모델이 느린 건지 서버가 죽은 건지" 구분할 수 없습니다.

```python
self._client = OpenAI(base_url=..., api_key=key, max_retries=0)
```

**`max_retries=0` 이 중요합니다.** SDK 는 기본적으로 알아서 재시도하는데,
켜두면 내가 짠 7.5초 예산을 SDK 가 몰래 3배로 늘려 씁니다.

**④ 예외를 벤더 것에서 우리 것으로 번역**

```python
except APITimeoutError      → JudgeTimeout        (503)
except AuthenticationError  → JudgeConfigError    (500)  "API 키를 확인하세요"
except NotFoundError        → JudgeConfigError    (500)  "모델 ID를 찾을 수 없습니다"
except RateLimitError       → JudgeRateLimit      (429)
except BadRequestError      → 파라미터 빼고 1회만 재시도 → 그래도 안 되면 JudgeUpstreamError
```

`BadRequestError` 만 특별 취급합니다. NIM 이 특정 샘플링 파라미터(`temperature`)를 거부하는 경우가
있어서, 한 번은 그것만 빼고 재시도합니다.

이 번역 덕분에 **서버는 `openai` 패키지를 import 하지 않아도 됩니다.** 벤더 격리의 실물입니다.

### 4.5 프롬프트 v1 (`prompts.py`)

프롬프트 문자열은 **이 파일에만** 존재합니다. 어댑터는 프롬프트를 만들지 않고 받아서 포장만 합니다.

**시스템 프롬프트의 설계 의도** — 목표가 두 개(정확도 80% / 오탐 0회)일 때
**둘이 충돌하면 어느 쪽을 버릴지** 모델에게 명시적으로 알려줍니다.

```
1. **확신이 없으면 DONE 을 쓰지 마십시오.** 애매하면 NOT_DONE 또는 CANNOT_TELL 입니다.
   틀린 DONE 은 사용자가 덜 익은 음식을 먹게 만듭니다.
   반대로 CANNOT_TELL 은 한 번 더 확인할 뿐이라 피해가 없습니다.
2. **사진에 보이는 것만 근거로 삼으십시오.** 경과 시간만으로 DONE 을 판정해서는 안 됩니다.
```

2번 규칙이 없으면 모델은 "5분이나 지났으니 익었겠지" 하고 **사진을 안 보고** 답합니다.
이건 LLM 의 매우 흔한 실패 방식입니다.

**checkType 힌트** — `COLOR_CHANGE` 라고만 던지면 모델은 무엇을 보라는 건지 모릅니다.

```python
CHECK_TYPE_HINT = {
```

### 4.6 `server.py` — 실제 판정 경로에서 새로 한 일

**① 모델에 보내기 전에 이미지를 검증한다**

```python
# server.py:97
def _validate_image(b64, field):
    if not b64 or not b64.strip():
        raise HTTPException(400, f"{field} 가 비어 있습니다")
    data = decode_b64_image(b64)                      # 실패 → 400
    if not looks_like_jpeg(data):                     # 앞 3바이트가 FF D8 FF 인가
        raise HTTPException(400, f"{field} 가 JPEG 가 아닙니다 (앞 3바이트 {data[:3].hex()})")
```

**JPEG 매직바이트**란 파일 맨 앞의 고정된 서명입니다. JPEG 는 항상 `FF D8 FF` 로 시작하고,
PNG 는 `89 50 4E`(`.PNG`)로 시작합니다.

**왜 여기서 잘라내나** — 깨진 base64 나 PNG 를 그대로 모델에 보내면 판정이 이상해지거나
벤더가 400 을 뱉는데, **원인 파악에 반나절**이 걸립니다. 여기서 잘라내면 2번은 오류 메시지의
`앞 3바이트 89504e` 를 보고 5초 만에 "아 PNG 를 보냈구나" 하고 압니다.

**② TIME_ONLY 는 조용히 판정하지 않고 400 을 준다**

```python
if req.checkType == "TIME_ONLY":
```

`smoke.py` 는 두 가지 모드로 판정 경로를 확인합니다.


HTTP 모드는 **두 시간을 나눠서** 찍습니다.

```
[1] DONE  VISIBLE_CHANGE  vlm 3210ms / 왕복 3245ms / 네트워크 35ms
                          └─ 서버가 잼    └─ 내가 잼    └─ 차이
```

이 분리 덕분에 아주 중요한 사실을 알아냈습니다.

> **네트워크는 20ms 수준. 느린 건 업로드가 아니라 모델 추론이다.**

그리고 **T0 단계의 지연 측정이 실제 성능이 아니었다**는 것도 드러났습니다.

| 조건 | base64 크기 | 성공 지연(중앙) | 타임아웃 |
|---|---|---|---|
| 합성 이미지 2장 (T0 측정) | 23KB | **1.8s** | 0/4 |
| 실사진 긴변 768 · 2장 | 199KB | **3.2s** | 0/3 |
| 실사진 긴변 1024 · 2장 | 319KB | **3.8s** | **2/5** |
| 실사진 긴변 1024 · 1장 | 160KB | 3.0s | **2/3** |
| 실사진 긴변 1024 · 2장 (**백업 8b 모델**) | 319KB | 3.5s | 0/3 |

**읽어야 할 것 세 가지**

1. **합성 이미지로 잰 1.8초는 실제 성능이 아니었다.** 실사진에서는 3초를 넘습니다.
   명세서 12절 #4(왕복 3초)는 현재 조합으로는 **미달**입니다
2. 이미지를 줄이면 지연도 줍니다 → 1번에게 요청한 "긴 변 1280" 은 재검토 대상
3. **오늘의 지배적 원인은 크기가 아니라 12b 모델의 변동성**입니다.
   1장(160KB)에서도 3회 중 2회가 예산을 넘겼는데, 같은 시각 8b 모델은 7회 전부 성공했습니다

**여기서 백엔드를 바꾸지 않은 이유** — 8b 는 지연이 안정적이지만 색 판별이 부정확했습니다
("파랑"→"보라"). 이 프로젝트의 1순위 리스크는 지연이 아니라 **오탐**입니다.
**정확도를 재기 전에는 바꾸지 않습니다**(T2-3에서 결정). 대신 완화책을 넣었습니다.

- 서버 예산 7.5초 → 앱이 소켓 타임아웃 대신 서버의 503 메시지를 받음
- 타임아웃은 503 이며 CANNOT_TELL 이 아님 → F4-5 카운터에 영향 없음
- 2번은 503 을 받으면 1회 재시도 후 다음 검사 주기로 넘김

> 💡 초보자용 교훈: **성능 측정은 실제 데이터로 해야 합니다.**
> 합성 이미지로 잰 숫자를 믿고 계획을 세웠다면 W3 시연에서 처음 문제를 만났을 것입니다.

## 5. Phase 2 — 평가 하네스 (`eval.py`)

### 5.1 왜 촬영(T2-1)보다 평가 코드(T2-2)를 먼저 만들었나

계획서에는 T2-1 → T2-2 순서였는데 **의도적으로 뒤집었습니다.** 이유 두 개:

**① 지표 계산은 실제 사진으로 검증할 수 없다**

30쌍을 돌려 "정확도 61%" 가 나와도, 그 61% 가 **맞게 계산된 값인지 확인할 방법이 없습니다.**
정답과 응답을 **둘 다 아는 상태**로 돌려야 검산이 됩니다.

**② 라벨링(4h)이 촬영(3h)보다 비싸고 되돌리기 어렵다**

30쌍을 라벨링한 뒤에 "필드가 빠졌네"를 발견하면 그 4시간이 날아갑니다.
평가 코드를 먼저 쓰면 **스키마 결함이 라벨링 전에** 드러납니다.

실제로 이 순서 덕분에 결함을 하나 잡았습니다(다음 절).

### 5.3 지표 — "정확도 하나"로는 목표를 못 잰다

명세서 12절의 목표는 **두 개**입니다.

```
① A등급 정확도 80% 이상
② 확신 있는 오답(오탐) 0회
```

이 둘을 합쳐 "전체 정확도 85%" 라고 보고하면 **오탐 4건이 그 안에 숨습니다.**
그래서 등급별로 나누고 오탐을 따로 셉니다.

**오탐(false accept) vs 미탐(false reject) — 반드시 구분해야 하는 이유**

```python
# eval.py:203
@property
def false_accept(self):    # 🚨 완료가 아닌데 DONE — 목표 0회
    return self.label.groundTruth != "DONE" and self.verdict == "DONE"

@property
def false_reject(self):    # 미탐 — 완료인데 NOT_DONE (안전한 실패)
    return self.label.groundTruth == "DONE" and self.verdict == "NOT_DONE"
```

| | 무슨 일이 벌어지나 | 심각도 |
|---|---|---|
| **오탐** | 안 익었는데 다음 단계로 넘어감 → **덜 익은 음식** | 🚨 목표 0회 |
| 미탐 | 다 익었는데 "아직"이라고 함 → 20초 뒤 다시 확인 | 참고 지표 |

같은 "오답 1건"이지만 피해가 완전히 다릅니다. 하나의 정확도 숫자로 합치면 이 차이가 사라집니다.

**등급 매핑** (명세서 5.1):

```python
GRADE = {"PRESENCE": "A", "IDENTIFY": "A",              # 쉬움 — 존재·식별
         "COUNT": "B", "COLOR_CHANGE": "B", "STATE_CHANGE": "B",   # 어려움
         "TIME_ONLY": "-"}                              # 사진으로 판정 안 함
```

DoD 가 "A등급 80%" 이므로, 등급 매핑이 없으면 **DoD 를 계산할 수조차 없습니다.**

**리포트가 출력하는 것**: 전체 지표 → DoD 통과 여부 → 등급별 → checkType별 → 혼동 행렬 → 오답 목록(오탐을 맨 위로).

**혼동 행렬(confusion matrix)** 은 "정답 × 판정" 표입니다.

```
               DONE     NOT_DONE  CANNOT_TELL
  DONE            8            2            1
  NOT_DONE      🚨2            9            0     ← 이 칸이 오탐
  CANNOT_TELL     0            1            4
```

대각선이 정답이고, **왼쪽 아래 칸들이 오탐**입니다. 여기에 🚨 를 찍어 눈에 띄게 했습니다.

**종료 코드로도 알립니다** — CI 나 반복 실행에서 유용합니다.

```python
passed = a.n and a.accuracy >= 0.80 and m.false_accept <= 0
return 0 if passed else 2
```

### 5.6 `imageprep.py` — 원본을 절대 건드리지 않는다

**가장 중요한 규칙 한 줄:**

> (원본 프로파일이 없으면 무엇에서 무엇으로 변환할지 알 수 없기 때문).
> Gmail·USB 로 받은 원본은 ICC 가 살아 있어 정상 동작하지만,
> **메신저를 거쳐 ICC 가 지워진 파일은 `--srgb` 를 켜도 변환되지 않습니다.**
> A/B 실험 전에 `inspect_image.py` 로 ICC 열이 `P3` 인지 먼저 확인하세요.

**EXIF 는 저장하지 않습니다** — 회전은 이미 픽셀에 반영돼 있고(`Orientation=1`),
GPS 같은 개인정보가 평가 산출물로 새어 나가지 않게 하기 위해서입니다.

### 5.7 `inspect_image.py` — 규격 감사 도구

```bash
python inspect_image.py testdata/raw/        # 폴더 통째로도 됨
```

출력하는 것: 해상도 · 포맷 · 모드 · **Orientation** · **ICC** · 파일 크기 · base64 예상 크기,
그리고 촬영 기기 분포 / 해상도 분포 / 가로세로 비율 이상치.

**기기 확인이 왜 있나** — 평가셋에 폰 사진이 섞이면 **화각이 달라 평가가 오염됩니다.**

```python
EXPECTED_MODEL = "Ray-Ban Meta Smart Glasses 2"
```

EXIF 의 Make/Model 을 읽어 안경 외 기기가 섞였는지 잡아냅니다.

## 6. 이미지 파이프라인에서 알아낸 사실 (전부 실측)

이 절의 내용은 문서를 읽어서가 아니라 **파일을 직접 열어 확인한** 것들입니다.

### 6.1 메신저는 파일을 조용히 망가뜨린다

| 항목 | 디스코드 경유 | Gmail(파일 첨부) 경유 |
|---|---|---|
| EXIF | **0개** — 통째로 삭제 | ✅ 9~10개 온전 |
| ICC 프로파일 | 없음 | ✅ 520 bytes 온전 |
| 용량 | 원본보다 감소 (**재압축됨**) | ✅ 1,643 / 1,907 KB 무손상 |

**진짜 문제는 이겁니다**: EXIF 가 비어 있으면
**1번 코드가 잘해서인지 디스코드가 지워준 건지 구분할 수 없습니다.** 파이프라인 검증이 무의미해집니다.

> Gmail 이라도 안드로이드 공유 시트에서 **"사진"이 아니라 "파일"로** 첨부해야 합니다.

### 6.2 EXIF 회전 — "가장 위험"으로 지목했다가 해당 없음으로 판명

원래 이게 최대 위험 요소였습니다.

```
카메라: 사진은 눕혀서 저장하고, EXIF에 "90도 돌려서 봐라"라고만 적어둠
앱  → EXIF 읽음 → 똑바로 보임        ✅
서버 → AI      → EXIF 무시 → 누운 사진  ❌
결과: "팬이 안 보인다" → CANNOT_TELL 무한 반복
```

**앱 화면은 멀쩡한데 판정만 계속 실패**하는 형태라 원인 찾는 데 반나절이 갑니다.

실제로 검사해보니 **안경 원본 2장 모두 `Orientation = 1`** 이었습니다.
안경이 이미 픽셀에 회전을 반영해 저장합니다. **처리 불필요.**

다만 **축소·재인코딩 과정에서 회전 태그가 새로 붙을 수 있으므로**,
1번에게 "축소 후에도 Orientation 이 1인지 확인만" 요청했습니다.

### 6.3 색공간 — 안경은 Display P3 로 저장한다

ICC 프로파일 실측값: **`Display P3 Gamut with sRGB Transfer`**
`mode` 는 `RGB` 로 보이지만 **픽셀값이 sRGB 기준이 아닙니다.**

P3→sRGB 변환 시 평균 채도가 **13.5%** 변합니다(두 장 모두 같은 방향).
절대 화소 차이는 저채도 구간에서 1.7/255 로 작지만, **편향 방향이 일정**해서
COLOR_CHANGE 판정에 영향을 줄 수 있습니다.

→ 그래서 **변환은 서버에서, 플래그로** 합니다. 1번에게는 "색공간을 건드리지 마세요"라고 요청했습니다.
앱에서 미리 변환하면 A/B 실험 자체가 불가능해지니까요.

**판단 기준 한 줄**:

> **용량이 변하는 것만 1번이, 나머지는 서버가 한다.**

축소는 4.7MB → 200KB 로 줄이므로 **반드시 업로드 전**이어야 합니다.
색공간 변환은 용량이 변하지 않으므로 클라이언트에서 할 이유가 없습니다.

### 6.4 안경이 촬영마다 다른 해상도를 낸다

```
2765x3687   2766x3688   2792x3725   3024x4032   1376x1824(영상)
```

전부 같은 안경(`Meta / Ray-Ban Meta Smart Glasses 2`)에서 나온 것입니다.
비율은 3:4 로 같지만 픽셀 수가 다릅니다. 긴 변 1280 으로 맞추면 짧은 변이 **959~966 으로 갈립니다.**

**이건 정상이고 VLM 판정에 지장 없습니다.** 여기서 "960 고정"을 요구하면
1번이 **늘리거나(왜곡) 잘라내야(내용 손실)** 합니다.
중요한 건 크기가 똑같은 게 아니라 **배율이 일정하고 왜곡이 없는 것**입니다.

### 6.5 `raw/` 를 따로 두는 이유

```
긴 변 1280 → 1024 로 변경?        raw/ 에서 다시 만들면 끝
P3 → sRGB 로 정책 변경?           raw/ 에서 다시 만들면 끝
1번 축소본과 안 맞는 걸 발견?      raw/ 에서 다시 만들면 끝

raw/ 없이 정규화본만 남겼다면 → 위 전부 재촬영 (촬영 3h + 라벨링 4h)
```

**규격 변경을 "재촬영"이 아니라 "재생성"으로 바꾸는 안전장치**입니다.
T2-1 에서 규격이 바뀔 가능성이 실제로 높기 때문에(§4.7 지연 실측) 특히 중요합니다.

## 9. 초보자용 용어 사전

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **VLM** | Vision Language Model. 이미지+텍스트를 함께 받는 언어 모델 | Nemotron 12b |
| **base64** | 바이너리(사진)를 문자로 바꾼 인코딩. **크기가 약 1.34배 늘어남** | JSON 본문에 사진을 실어 보내는 방법 |
| **매직바이트** | 파일 맨 앞의 고정된 서명 | JPEG = `FF D8 FF`, PNG = `89 50 4E` |
| **EXIF** | 사진에 붙은 메타데이터(촬영 기기·시각·GPS·회전) | 안경 확인·회전 함정·개인정보 |
| **ICC 프로파일** | "이 픽셀값이 어떤 색을 뜻하는가"의 기준 | 안경은 Display P3 |
| **무상태(stateless)** | 서버가 이전 요청을 기억하지 않음 | DB 불필요, 상태는 앱이 관리 |
| **어댑터 패턴** | 벤더별 차이를 한 겹 감싸 안쪽 코드를 보호 | `judge/` 폴더 |
| **Protocol** | "이 모양만 갖추면 OK"라는 파이썬 규격 선언 | `VlmJudge` |
| **폴백(fallback)** | 실패했을 때 떨어질 안전한 기본값 | `CANNOT_TELL` |
| **오탐 / 미탐** | 아닌데 맞다고 함 / 맞는데 아니라고 함 | 오탐 = 🚨 목표 0회 |
| **불변식(invariant)** | 어떤 입력에도 항상 참이어야 하는 성질 | "쓰레기 입력에서 DONE 금지" |
| **DoD** | Definition of Done. 완료를 판단하는 객관적 기준 | "A등급 80% + 오탐 0" |
| **게이트 태스크** | 결과에 따라 이후 계획이 바뀌는 실험 | T0-2 다중 이미지 |
| **혼동 행렬** | 정답×판정 표. 어떤 오답이 많은지 한눈에 | `eval.py` 리포트 |
| **콜드 스타트** | 잠들었던 서버가 처음 깨어날 때의 지연 | 무료 티어 15분 슬립 → 30초+ |
| **백오프** | 실패 후 점점 간격을 늘려 재시도 | 429 대응 (T2-6) |
| **레이트 리밋** | 단위 시간당 요청 수 제한 | 429 응답 |

## 11. 이 프로젝트에서 배운 것 (기술 외)

초보 개발자에게 가장 전달하고 싶은 것은 코드가 아니라 **의사결정의 순서**입니다.

| 원칙 | 이 프로젝트에서의 실물 |
|---|---|
| **팀을 막는 것부터 푼다** | 내 코드 완성도보다 T0-3(Mock)이 우선. 2번이 그날부터 개발 시작 |
| **계획을 바꿀 실험을 먼저 한다** | T0-2 게이트를 첫날에. 2주 뒤 발견했으면 계획을 갈아엎어야 했음 |
| **측정 도구를 측정 대상보다 먼저 만든다** | `eval.py` 를 촬영보다 먼저 → 라벨링 4시간 전에 스키마 결함 발견 |
| **검증할 수 없는 숫자는 믿지 않는다** | `--selftest` 로 지표 계산 자체를 검산 |
| **실제 데이터로 재측정한다** | 합성 이미지 1.8초 → 실사진 3.8초. 목표 미달을 W1에 발견 |
| **되돌릴 수 있게 만든다** | `raw/` 보관 → 규격 변경이 재촬영이 아니라 재생성 |
| **실패의 방향을 정해둔다** | 애매하면 항상 CANNOT_TELL. 오탐은 사용자가 다치고, 미탐은 20초 더 기다릴 뿐 |
| **줄어든 요청도 명시적으로 전달한다** | 조용히 빼면 상대는 이전 판대로 구현해 버림 |
