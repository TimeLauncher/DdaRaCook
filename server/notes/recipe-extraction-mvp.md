# YouTube 레시피 추출 MVP 실영상 검증 기록

기준일: 2026-08-24
대상: `POST /extract-recipe`의 실제 YouTube 자막 조회 + NVIDIA 모델 호출
목적: 다음 작업에서 같은 실패를 반복하지 않고 모델·프롬프트·후처리 변경을 비교하기 위한 기준선

## 현재 기준 설정

- 자막: `youtube-transcript-api` 직접 조회(한국어 우선)
- 구조화 모델: `meta/llama-3.1-8b-instruct`
- 모델 제한: 1회 90초, 시간 초과만 1회 재시도
- 앱 읽기 제한: 200초
- 분량 누락: `분량 미상`으로 보완하고 경고
- 불완전한 자동 판정: `TIME_ONLY`, `isAutoCheck=false`로 강등하고 경고
- 결과는 저장 전 사용자가 고치는 초안이며 `isMvpReady=false`

MVP 통과 기준은 HTTP 200과 앱 `Recipe` 계약 파싱 성공이다. 자막 오인식이나 재료 누락이 있으면
`편집 필수`로 분류한다. 자동 판정이 안전하게 강등된 것은 계약 통과이지만 판정 품질 통과는 아니다.

## 영상별 관찰

### `5u1HOrepKMo`

- 자막의 `산미`를 재료 `삼미`로 잘못 사용했다.
- 핵심 재료인 닭이 재료 목록에서 빠졌다.
- `7~8분 + 4~5분` 안내와 `maxExpectedSeconds=120`이 모순됐다.
- 한 장의 화면으로 판정하기 어려운 조건을 자동 판정 조건으로 만들었다.
- 불완전한 레시피 영상에는 422를 반환하는 충분성 검사가 필요하다는 근거가 됐다.

### `IsHR3hDmqSY`

- 텍스트 전용 모델로 바꾼 뒤 응답 시간이 1분 이상에서 9.4초로 줄었다.
- 자막 오인식 `하인한 치킨 나이스`, `다진 생각`이 단계 문장에 남았다.
- 쌀/밥, 닭지방, 식용유가 재료 목록에서 빠졌지만 단계에서는 사용됐다.
- 자동 판정 메타데이터가 불완전해 8단계 모두 수동 진행으로 강등됐다.
- 링크 입력부터 앱 계약 반환까지의 기술 경로 검증용 빠른 회귀 영상으로 사용한다.

### `NqsgtHMHfu4`

- 본요리 뒤의 간장 소스와 칠리 소스가 각각 9·10단계로 포함됐다.
- 두 소스는 별도 레시피나 선택 분기로 분리되지 않고 본 레시피의 연속 단계로 합쳐졌다.
- 재료에 `청주`가 중복됐고 `다진 마늘`/`다진마늘` 표기가 분리됐다.
- 쌀/밥, 식용유, 육수가 재료 목록과 단계 사이에서 일관되지 않았다.
- `10분 끓이기 + 5분 뜸`인데 6단계 `maxExpectedSeconds`가 300초라 시간 합계가 맞지 않았다.
- `청경체`, `당육수`, `식용을 살짝 두은` 등 자막 오인식이 그대로 남았다.
- 11단계 모두 자동 판정 정보가 불완전해 수동 진행으로 강등됐다.
- 복수 소스까지 놓치지 않는지는 통과했지만, 분기 표현·재료 정규화·시간 교차검증은 미통과다.

## 배포 환경 차단 (2026-08-25 확인)

위 실영상 결과는 **전부 로컬 IP에서 낸 것이고 Render에서는 한 번도 검증하지 않았다.** 앱 연동
시점에 드러난 사실은 다음과 같다.

- 라이브 `POST /extract-recipe` 는 `IsHR3hDmqSY` 에 대해 **0.87초 만에 HTTP 503** 을 낸다.
- 응답은 `recipe_extractor.py` 의 `RequestBlocked`/`IpBlocked` 분기 메시지다. 즉 모델 지연이나
  자막 부재가 아니라 **Render 데이터센터 IP에 대한 YouTube 차단**이다.
- 당시 `/health` 는 `transcriptProvider: "direct"`, `proxyConfigured: false` 였다.

`youtube-transcript-api` 직접 조회는 클라우드 IP에서 신뢰할 수 없다. 로컬 통과를 배포 통과로
읽지 않는다. 기준선 표를 갱신할 때는 로컬인지 Render인지 반드시 함께 적는다.

해결은 `YOUTUBE_TRANSCRIPT_API_KEY`(호스팅 자막 API) 또는 `YOUTUBE_PROXY_URL`(프록시) 중 하나를
Render 환경변수에 넣는 것이다. 호스팅 경로(`_hosted_transcript`)는 이때까지 실제 호출 이력도
테스트도 없었으므로, 공식 문서 대조 후 다음을 고쳤고 회귀 테스트 4건을 추가했다.

- 직접 조회가 `ko` 를 먼저 찾는 것과 달리 언어 선호를 보내지 않았다 → `language: "ko"` 추가.
- 자막이 없어 ASR 작업으로 넘어간 `202` 가 2xx라서 `ok` 검사를 통과하고 "자막 없음" 422로
  둔갑했다 → `202` 를 명시적으로 끊고 음성 변환 필요 메시지를 낸다.

`format` 은 문자열이 아니라 `{timestamp, paragraphs, words}` 불리언 객체이고 `segments[].start`
는 밀리초다. 기존 코드가 맞았으며 테스트로 고정했다.

### 해결 확인 (Render, 2026-08-25)

`YOUTUBE_TRANSCRIPT_API_KEY` 를 Render에 넣고 재배포한 뒤 `/health` 가
`transcriptProvider: "hosted"` 로 바뀌었고, `IsHR3hDmqSY` 가 **21.6초 만에 HTTP 200** 을
반환했다. 자막 언어 `ko`, 재료 6개·단계 6개, `isMvpReady: false` 로 앱 계약을 만족한다.
**배포 환경에서 처음으로 통과한 기록이다.**

다만 같은 영상을 로컬 직접 조회로 돌렸을 때의 재료 8개·단계 8개와 결과가 다르다. 호스팅
서비스가 돌려주는 자막이 직접 조회본과 동일하지 않다는 뜻이므로, 기준선을 비교할 때는
자막 출처(direct/hosted)도 함께 적는다.

품질 문제는 자막 경로와 무관하게 그대로다. 6단계 전부 자동 판정 정보가 불완전해 수동으로
강등됐고, 재료 6개가 모두 `분량 미상`이며, 밥/쌀·식용유·닭지방은 단계에서 쓰이는데 재료
목록에 없다. `청경체`, `당육수`, `식용을 살짝 두은`, `다진 생각` 등 자막 오인식도 남아 있다.
즉 **차단 해소는 기술 경로 복구이지 추출 품질 개선이 아니다.** 아래 우선순위는 유효하다.

무료 크레딧은 10건이고 이 검증에 1건을 썼다. 남은 9건은 발표 시연용으로 아낀다.

## 실험 하네스와 기준선 (2026-08-25)

`recipe_lab.py` 로 자막을 캐시해 모델·프롬프트를 무료로 반복 실험한다. **크레딧은 자막 조회에만
들고 모델 호출은 NVIDIA 키라 무료다.** 자막 한 번 받아두면 실험은 공짜다.

    python recipe_lab.py fetch <url>                      자막 캐시 (크레딧 1건)
    python recipe_lab.py run <videoId> --label X [--model M] [--fewshot on|off]
    python recipe_lab.py diff <videoId> A B               두 실행 비교
    python recipe_lab.py score gold:beef-brisket-pasta    정답 점수표

기준 영상은 `SSbyRvzf1VQ`(우삼겹 파스타 정답의 출처)다. 손으로 만든 정답이
`testdata/gold/beef-brisket-pasta.json` 에 있어 입력↔정답 쌍이 된다. 단, 정답에는 사람이
원문에 없는 판단(면 8분 타이머, 냉동면→일반면)을 넣었으므로 **일치가 아니라 스타일 기준**이다.

### 모델 지연 실측 (같은 짧은 프롬프트 2회)

| 모델 | 1회 | 2회 |
|---|---|---|
| `meta/llama-3.1-8b-instruct` | 0.7초 | 0.1초 |
| `meta/llama-3.3-70b-instruct` | 63.2초 | 타임아웃 |
| `openai/gpt-oss-120b` | 0.4초 | 0.2초 |
| `nvidia/llama-3.3-nemotron-super-49b-v1.5` | 7.7초 | 14.4초 |
| `nvidia/nemotron-3-super-120b-a12b` | 0.5초 | 0.9초 |

**무료 티어에서는 모델 크기와 속도가 비례하지 않는다.** 70B는 대기열 때문에 사용 불가고,
120B급 두 개가 8B만큼 빠르다. `nemotron-3-super-120b` 는 실제 추출에서 503으로 실패했다.

### `SSbyRvzf1VQ` 결과

| 설정 | 결과 | 자동 판정 | 분량 미상 | 기준 사진 |
|---|---|---|---|---|
| `llama-3.1-8b` (현재 배포본) | **실패** — 잘못된 checkType | - | - | - |
| `gpt-oss-120b`, 예시 없음 | 18.4초 성공 | 3/7 | 9/9 | 0 |
| `gpt-oss-120b`, 예시 있음 | 25.1초 성공 | **6/7** | 7/11 | 2 |
| 정답(사람) | - | 8/8 | 0/9 | 2 |

배포 중인 8B는 이 영상에서 아예 실패한다. `gpt-oss-120b` + 예시 조합이 자동 판정을 3/7에서
6/7로 올렸고, 자막 오인식(`우상겹`→`우삼겹`, `다진바늘`→`다진 마늘`, `진간푼`→`진간장`)을
교정한 뒤 무엇을 고쳤는지 경고에 남겼다. `parallelTimer` 는 자막에 있는 30초 불리기를 썼고
정답의 480초를 베끼지 않았다 — 없는 값을 지어내지 않는다는 뜻이다.

### 이때 알아낸 것

- **`SYSTEM_PROMPT` 의 "단순 투입 행위는 TIME_ONLY" 규칙이 정답 fixture와 모순이었다.**
  정답은 투입을 PRESENCE 자동 판정으로 쓴다. 예시를 붙이자 모델이 두 지시 사이에서 안전한
  쪽으로 도망가 전 단계를 TIME_ONLY 로 만들었다(자동 판정 0/6). 규칙을 고치자 6/7이 됐다.
  **예시를 넣기 전에 기존 프롬프트와 충돌하는 규칙이 없는지 먼저 본다.**
- 예시에 "못 채우겠으면 TIME_ONLY 로 만들어라" 같은 도피로를 주면 모델이 전부 그리로 간다.
  요구를 긍정형으로 쓰고 기대치를 숫자로 준다("절반 이상이 자동 판정으로 나온다").
- **reasoning 모델은 `max_tokens` 4000으로 부족하다.** 사고 과정이 먼저 토큰을 먹어 JSON이
  잘린다. 기본값을 12000으로 올렸다.

### 모델 전수 조사 (27개 시도, 4개 생존)

NVIDIA NIM 카탈로그 102개 중 텍스트 후보 68개에서 27개를 실제 추출 작업으로 시험했다.
**23개가 탈락했다.** 0.5초 만에 503이 나면 이 계정·엔드포인트에서 chat 호출이 안 되는
모델이고, 60초 컷에 걸리면 Render 에서는 더 느릴 테니 어차피 못 쓴다.

탈락 예: `llama-3.3-70b`, `llama-3.1-70b`, `kimi-k2.6`, `kimi-k3`, `gemma-4-31b`,
`mistral-large-2`, `nemotron-4-340b`, `nemotron-3-ultra-550b`, `deepseek-v4-flash`,
`step-3.7-flash`, `phi-3.5-moe`, `yi-large`, `dbrx-instruct`, `jamba-1.5-large` 등.

**무료 티어에서는 모델 크기·명성과 사용 가능 여부가 무관하다.** 카탈로그에 있다고 쓸 수
있는 게 아니므로, 후보를 고를 때는 반드시 실제 작업으로 먼저 찔러본다.

생존한 넷 (`SSbyRvzf1VQ`, 예시 있음, 로컬 측정):

| 모델 | 시간 | 자동 판정 | 분량 미상 | 단계 | 비고 |
|---|---|---|---|---|---|
| `meta/llama-3.1-8b-instruct` | 8초 | — | — | — | **검증 실패**(잘못된 checkType) |
| `openai/gpt-oss-120b` | 25~35초 | 80~89% | 7/11 | 7~9 | 7회 중 1회 전 단계 TIME_ONLY 붕괴 |
| `nvidia/nvidia-nemotron-nano-9b-v2` | 50~70초 | 67~86% | **0/8** | 7~9 | 느리고 자동 판정 편차 큼 |
| **`minimaxai/minimax-m3`** | 22~78초 | 83~88% | 1/10 | 6~8 | 붕괴 없음, 오인식 교정 우수 |

`minimax-m3` 를 기본으로 정했다. 분량 표기(1/10)와 자동 판정 안정성이 가장 낫고 붕괴
모드가 없다. `nemotron-nano-9b-v2` 는 분량이 0/8로 더 낫지만 일관되게 2배 느려
Render 에서 타임아웃 위험이 크다.

### 벤치마크 오염 주의

few-shot 예시에 "우삼겹을 볶는다 → COLOR_CHANGE, 붉은 부분이 줄었는가"를 넣었더니
기준 영상이 바로 그 우삼겹 파스타라 모델이 예시 문장을 그대로 베꼈다. 예시를 양파로
바꾸자 품질이 유지됐으므로 학습은 된 것이지만, **예시에 기준 영상의 정답을 넣지 않는다.**

### 단계 뭉침

`minimax-m3` 는 "썰고 넣고 볶는다"를 한 단계로 묶어 5~6단계만 냈다. 동작 하나 단위로
끊으라는 지침을 넣자 6~8단계가 됐다(정답 8단계). 프롬프트로 고쳐지는 문제였다.

### 남은 문제

- 분량 미상 7/11. 자막의 `한 대`·`하나`·`두어장` 을 표준 표기로 못 옮긴다. 정답은 0/9다.
- 자막 오인식 `배추 모양`(둥지 모양 추정)을 재료 `배추` 로 만든다.
- 자동 판정 6/7이지만 `COLOR_CHANGE` 를 안 쓰고 `STATE_CHANGE` 로 몰린다.

## 다음 개선 우선순위

1. 단계에서 사용한 재료와 최상위 `ingredients`를 양방향 비교해 누락·중복·띄어쓰기 차이를 경고한다.
2. instruction의 시간 합계와 `inspectionPolicy.maxExpectedSeconds`를 교차검증한다.
3. `두 가지 중 선택` 같은 자막을 병렬 단계가 아니라 선택 분기로 표현할 계약을 결정한다.
4. 알려진 음식명과 같은 자막 오인식만 제한적으로 보정하되, 수량·시간은 추측하지 않는다.
5. 모든 단계가 수동으로 강등되면 모델의 자동 판정 생성 품질을 별도 경고한다.
6. 짧은 소개·요약 영상에는 레시피 충분성 점수를 적용해 필요하면 422로 거부한다.

## 재현 시 주의

- 외부 모델 지연 때문에 시간은 매번 달라질 수 있다.
- API 키와 팀 토큰은 `.env`에서만 읽고 기록이나 명령에 실제 값을 남기지 않는다.
- 현재 MVP는 영상 프레임이나 원본 오디오를 분석하지 않고 YouTube 자막만 사용한다.
- 모델·프롬프트·후처리를 바꾼 뒤에는 위 세 링크를 다시 실행하고 이 표에 새 결과를 추가한다.
